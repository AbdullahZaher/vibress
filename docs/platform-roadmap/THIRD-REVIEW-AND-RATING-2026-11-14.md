## New findings R26–R34

| ID | Priority | Finding / why previous plan is incomplete | Required English-plan correction and owners | Implementation acceptance evidence |
| --- | --- | --- | --- | --- |
| **R26** | **Critical security design** | The current [runtime role](../../packages/database/src/runtime-role.ts) grants `EXECUTE ON ALL FUNCTIONS IN SCHEMA public` and future function grants. **Even if these role-specific grants are revoked, PostgreSQL normally grants EXECUTE on new functions to PUBLIC**. SECURITY DEFINER functions also require safe search_path and ownership review. | [Effective ACL and RLS threat model](POSTGRES-PRIVILEGE-AND-RLS-THREAT-MODEL.md), M02 role migration and M05 plugin provisioning review. Owner: DB + Security. | Actual `has_function_privilege`/catalog tests for direct, inherited and PUBLIC grants, preexisting/default functions, SECURITY DEFINER functions and upgrade/rollback. |
| **R27** | **High security design** | PostgreSQL RLS policies are not necessarily a simple AND: **permissive policies combine via OR**, and RLS does **not** control `TRUNCATE` or `REFERENCES` privileges. Adding a second broad policy may silently widen access. | Define a least-privilege policy composition model and effective policy review with tests on each generated table. | Two conflicting policies, insert/update WITH CHECK, actor/tenant cross-ref, TRUNCATE/REFERENCES privilege denial, owner/BYPASSRLS all tested on supported PG. |
| **R28** | **High topology** | “One application per installation with separate credentials” is **not** physical isolation if two installations still share writable `public` schema/table grants. A Redis key prefix or S3 object prefix likewise does not enforce isolation without ACL/IAM boundaries. | Formalize v1 supported isolation: prefer **dedicated database + runtime/migration credentials per app installation**, separate Redis ACL/instance and bucket/access point IAM as appropriate; record exceptions. | Independent app A/B credentials provably cannot access each other's SQL/schema, queue keys, object data, secrets or backups; restore per installation. |
| **R29** | **Critical trust-model clarity** | Custom code-first app handlers execute as trusted server code within *their own* installation. They can potentially issue arbitrary SQL if they obtain that installation's credentials. **Tenant RLS based on writable custom GUCs is not a sandbox against malicious arbitrary SQL.** Prior docs risk overstating mediation boundaries. | Define trusted app-author vs untrusted end-user vs approved plugin vs arbitrary third-party code; prohibit shared untrusted process hosting for v1; state limits of in-process policy and enforced isolation. | Threat matrix demonstrates end-user isolation, app-to-app isolation and explicit non-guarantees for malicious same-process owner code; no claim of sandbox from TS types or GUCs. |
| **R30** | **High reliability** | Expand/contract is documented but mixed app/worker/SDK deployments, concurrent rollouts, partially completed backfills and long-running jobs need a concrete **version-skew contract** and abort/forward-fix runbook. | Add [rolling upgrade matrix and migration drill](UPGRADE-COMPATIBILITY-AND-DEPLOYMENT.md) to M03/M05/M06/M08/M11. | Old/new API+worker and schema version combinations tested, locks/idempotence, stuck/backfill recovery, rollback/replay ownership and measured recovery. |
| **R31** | **Medium–High execution** | The 13-milestone program has a GA cut, but no **dated evidence-backed discovery experiments, capacity allocation or explicitly testable market differentiation**; UX competitiveness claims remain speculation. | M00 product hypothesis and feasibility spike; M04/07 interview/clean install benchmark against actual matched competitor tasks, with stop/pivot criteria. | User research and repeatable developer onboarding tasks, real owner/capacity estimate; no invented dates/market superiority. |
| **R32** | **Medium quality gate** | CI currently runs broad build/test/image/E2E workflows but the proposed **roadmap-specific Markdown link/epic/ADR checker has not been implemented**; prior manual link validation cannot be claimed as CI evidence. | M00 adds a deterministic docs validator and required check; meanwhile this PR records only manual/static inspection results with SHA. | A real CI job verifies relative links, headings/anchors, unique `Mxx-Eyy`, score/rubric consistency, cross-doc release scope and issue links on the final SHA. |
| **R33** | **High integration boundary** | For app-per-installation architecture, **cross-application integrations must occur through explicitly authenticated APIs/events**, not by sharing SQL credentials, Redis or unsafely trusting incoming webhooks. | Add cross-install integration service contract and trust gates to M02/M06/M07/M11. | Scoped service accounts/token audience, signed/idempotent webhooks, origin/SSRF/egress restrictions, revocation and app A/B denial tests. |
| **R34** | **High authorization** | Per-installation Redis namespaces and storage prefixes alone are not sufficient access-control boundaries; caches also require correct app/tenant/principal scoping, and queue workers may otherwise process another installation's messages. | Explicit Redis ACL + queue credential/isolation policy and S3 bucket/IAM restrictions with authorized signed URL, plus cache key audit and reset drills. | Negative credential tests across Redis keys/jobs and object storage, verified no cross-install read/write/replay, emergency revocation. |

## Decision flow and closure priority

**First:** R26/R27/R28/R29 (effective SQL privileges, RLS composition, real physical isolation, code-trust model). These are design blockers before external app or multi-tenant runtime exposure. R30 and R33/34 are release/integration blockers as soon as workers, modules or multiple installs are supported. R31/32 must be assigned by M00 (product evidence and documentation CI).

**Documentation state:** These findings are corrected in the *proposed plan* by new detailed contracts and revised milestone tests; **no runtime fix is claimed**. A security finding is considered fixed only after source changes plus runnable negative tests, CI and approval on an immutable SHA.
